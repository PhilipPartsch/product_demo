.. _engineering-model:

Engineering model
=================

This section describes the need-type model of this project: which kinds of
needs exist, which fields and links they carry, and which rules
(``schemas.json``) both toolchains enforce. How needs are authored and
reviewed is described in :ref:`engineering-workflow`, how decisions and risks
are kept up to date in :ref:`engineering-decisions-risks`, and the CI gates
in :ref:`engineering-ci`.

Type model
----------

Each arrow points from a need to the need it links to.

.. mermaid::

   flowchart BT
     req["req<br/>Requirement"] -- satisfies --> us["us<br/>User Story"]
     arch["arch<br/>Architecture Element"] -- fulfills --> req
     spec["spec<br/>Specification"] -- refines --> arch
     impl["impl<br/>Implementation<br/>(code marker)"] -- implements --> spec
     tspec["test_spec<br/>Test Specification"] -- verifies --> spec
     result["testcase<br/>Test result<br/>(Sphinx-Test-Reports)"] -- executes --> tspec
     dec["dec<br/>Decision<br/>(nested in its parent)"] -. decides .-> any1(["any need"])
     risk["risk<br/>Risk"] -. affects .-> any2(["any need"])
     risk -. mitigated_by .-> mit(["req / arch / spec / test_spec / dec"])

Types
-----

.. list-table::
   :header-rows: 1
   :widths: 14 18 10 30 28

   * - Directive
     - Title
     - Prefix
     - Authored as
     - Links to
   * - ``us``
     - User Story
     - ``US_``
     - RST
     - —
   * - ``req``
     - Requirement
     - ``REQ_``
     - RST
     - ``satisfies`` → ``us``
   * - ``arch``
     - Architecture Element
     - ``ARCH_``
     - RST, with a component diagram on the page
     - ``fulfills`` → ``req``
   * - ``spec``
     - Specification
     - ``SPEC_``
     - RST
     - ``refines`` → ``arch``
   * - ``impl``
     - Implementation
     - ``IMPL_``
     - one-line codelinks marker in the source code
     - ``implements`` → ``spec``
   * - ``test_spec``
     - Test Specification
     - ``TSPEC_``
     - RST
     - ``verifies`` → ``spec``
   * - ``testfile`` / ``testsuite`` / ``testcase``
     - Test results
     - ``TF_`` (file id given in the ``test-file`` directive)
     - generated by Sphinx-Test-Reports from the pytest JUnit XML
     - ``executes`` → ``test_spec`` (``testcase`` only)
   * - ``dec``
     - Decision
     - ``DEC_``
     - RST, nested inside the need it decides about
     - ``decides`` → the parent and further needs
   * - ``risk``
     - Risk
     - ``RISK_``
     - RST
     - ``affects`` → any need; ``mitigated_by`` → ``req`` / ``arch`` /
       ``spec`` / ``test_spec`` / ``dec``

Every need has an explicit id matching ``^[A-Z]+_[A-Z][A-Z0-9_]*$``.

Where the needs come from:

- ``impl``: one-line markers in ``src/`` (Sphinx-Codelinks), for example
  ``# @Password check, IMPL_LOGIN, impl, [SPEC_LOGIN], false, true``
  (title, id, type, implemented specs, safety relevant, security relevant;
  all six are required). The page :ref:`full-impls` lives in ``src/`` and is
  mounted into these docs.
- Test results: pytest writes ``tests/_results/junit.xml``
  (``ubc script tests``); each test records the test specification it
  executes with ``record_property("executes", "TSPEC_…")``. The page
  :ref:`full-test-results` lives in ``tests/`` and is mounted into these docs.

Status
------

Only decisions and risks have a lifecycle, so only ``dec`` and ``risk``
carry the built-in ``status`` field; every other type has none. There is no
default: a field default would apply to every type. ``schemas.json``
requires an explicit status on ``dec`` / ``risk`` and forbids it elsewhere.

.. list-table::
   :header-rows: 1
   :widths: 20 45 35

   * - Type
     - Values
     - Final (needed for a release)
   * - ``dec``
     - ``proposed``, ``accepted``, ``superseded``
     - ``accepted``, ``superseded``
   * - ``risk``
     - ``open``, ``mitigated``, ``accepted``, ``closed``
     - ``mitigated``, ``accepted``, ``closed``

The other types are ready for a release when they are complete: covered
along the chain, decided, reviewed, and (for test results) passed.

Fields
------

.. list-table::
   :header-rows: 1
   :widths: 22 30 48

   * - Field
     - Types
     - Values
   * - ``safety_relevant``
     - all authored types (required)
     - ``true`` / ``false``
   * - ``security_relevant``
     - all authored types (required)
     - ``true`` / ``false``
   * - ``trust_boundary``
     - ``arch`` (required)
     - ``true`` / ``false``: the element takes input from outside or changes
       privileges
   * - ``test_level``
     - ``test_spec`` (required)
     - ``unit`` / ``integration`` / ``system``
   * - ``risk_category``
     - ``risk`` (required)
     - ``safety`` / ``security`` / ``technical`` / ``project`` /
       ``ai-workflow``
   * - ``severity``
     - ``risk`` (required)
     - ``low`` / ``medium`` / ``high``
   * - ``likelihood``
     - ``risk`` (required)
     - ``low`` / ``medium`` / ``high``
   * - ``recovered_from``
     - any (optional)
     - repository-relative source files a need was recovered from
       (``ubc agent reverse``)
   * - ``fp``
     - every need (derived)
     - content fingerprint (SHA-256 of id, type, title, status, tags,
       content, fields, links); used by the hash conditions of risk links
   * - ``parent``
     - every need (derived)
     - the need it is nested in (copy of ``parent_need``); used by
       ``dec-nested``

Safety and security relevance is set on each need; it is not inherited along
links.

Links
-----

.. list-table::
   :header-rows: 1
   :widths: 20 20 20 40

   * - Link
     - Outgoing
     - Incoming
     - From → To
   * - ``satisfies``
     - satisfies
     - satisfied by
     - ``req`` → ``us``
   * - ``fulfills``
     - fulfills
     - fulfilled by
     - ``arch`` → ``req``
   * - ``refines``
     - refines
     - refined by
     - ``spec`` → ``arch``
   * - ``implements``
     - implements
     - implemented by
     - ``impl`` → ``spec``
   * - ``verifies``
     - verifies
     - verified by
     - ``test_spec`` → ``spec``
   * - ``executes``
     - executes
     - executed by
     - ``testcase`` → ``test_spec``
   * - ``decides``
     - decides
     - decided by
     - ``dec`` → any need except ``dec``
   * - ``affects``
     - affects
     - affected by
     - ``risk`` → any need
   * - ``mitigated_by``
     - mitigated by
     - mitigates
     - ``risk`` → ``req`` / ``arch`` / ``spec`` / ``test_spec`` / ``dec``

Each link connects exactly one pair of types, so every edge of the model can
be checked on its own.

- ``decides`` is filled automatically: a decision nested in a need decides
  that need. Only a decision that decides further needs writes
  ``:decides:``, listing all targets, the parent first.
- ``affects`` and ``mitigated_by`` carry a hash condition on the target,
  ``TARGET[fp=="…"]`` (see :ref:`engineering-decisions-risks`); the pages
  show plain ids.

Schema rules
------------

``schemas.json`` is checked by ``ubc check`` (and the IDE) and by the Sphinx
build. A **violation** is always wrong and blocks every CI run. An **info**
finding marks something still incomplete: allowed on ``main``, but a release
needs zero.

.. list-table::
   :header-rows: 1
   :widths: 25 12 63

   * - Rule
     - Severity
     - Checks
   * - ``status-dec``, ``status-risk``
     - violation
     - ``dec`` and ``risk`` set a ``status`` from their own values (table
       above)
   * - ``status-none``
     - violation
     - no other type sets a ``status``
   * - ``fields-common``
     - violation
     - ``safety_relevant`` and ``security_relevant`` are set
   * - ``fields-test-spec``
     - violation
     - a ``test_spec`` has a ``test_level``
   * - ``fields-arch``
     - violation
     - an ``arch`` states ``trust_boundary``
   * - ``fields-risk``
     - violation
     - a ``risk`` has ``risk_category``, ``severity`` and ``likelihood``
   * - ``link-req-us``, ``link-arch-req``, ``link-spec-arch``,
       ``link-impl-spec``, ``link-tspec-spec``
     - violation
     - at least one up-link, and only to the allowed type
   * - ``link-result-tspec``
     - violation
     - a test result executes only test specifications
   * - ``link-dec``
     - violation
     - a decision decides at least one need, and no other decision
   * - ``dec-nested``
     - violation
     - a decision lives nested inside a need
   * - ``link-risk-affects``, ``link-risk-mitigation``
     - violation
     - a risk affects at least one need; mitigations are ``req`` /
       ``spec`` / ``test_spec`` / ``dec``
   * - ``risk-mitigated``
     - violation
     - a ``mitigated`` risk names at least one ``mitigated_by``
   * - ``risk-accepted``
     - violation
     - an ``accepted`` risk is decided by an ``accepted`` decision

Completeness rules (info):

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - Rule
     - Reports
   * - ``cov-us``, ``cov-req``, ``cov-arch``, ``cov-spec-impl``,
       ``cov-spec-test``, ``cov-tspec-result``
     - a need not yet covered downstream (user story without requirement,
       requirement without architecture element, architecture element
       without specification, specification without
       implementation or test specification, test specification without test
       result)
   * - ``dec-present``
     - a user story, requirement, specification or test specification
       without a decision
   * - ``result-passed``
     - a test result that did not pass
   * - ``risk-open``, ``dec-proposed``
     - a risk still ``open``, a decision still ``proposed``
